# Raw SQL in a TypeORM migration must match `SnakeNamingStrategy`

Live incident in `kubernetesqa` (staging), 2026-09-03, ~09:14–09:29 UTC.

## Symptom

`products` microservice throws on every Service Bus message for the Google Merchant feed job:
```
Unknown column 'ProductFeed__user__settings.order_webhook_url' in 'field list'
```
Message gets dead-lettered, then auto-resubmitted by the consumer's own DLQ-reprocessing loop (`ProductBusConsumerService.processDeadLetterQueue`, subscribes at `onModuleInit`), fails again, dead-lettered again — an infinite retry loop. ~700 failing attempts every 5 minutes, self-sustaining, invisible in Service Bus's DLQ metrics because it never accumulates (each message is drained and resubmitted as fast as it fails).

## Root cause

The kernel's DB connection uses `SnakeNamingStrategy` (`typeorm-naming-strategies`). An entity property with no explicit `@Column({ name: ... })` override gets its DB column name **auto-derived** from the property name in snake_case:
```ts
@Column('varchar', { length: 2048, nullable: true })
orderWebhookUrl: string;   // → entity expects column `order_webhook_url`
```

But the migration that added the column was hand-written raw SQL, not generated by `typeorm-cli`, and used the TypeScript property's literal casing instead of running it through the naming strategy:
```ts
await queryRunner.query(`ALTER TABLE \`user_settings\` ADD \`orderWebhookUrl\` varchar(2048) NULL`);
```
→ created `orderWebhookUrl` (camelCase) in the actual DB, which the entity/naming-strategy combo never queries for.

## The fix

`ALTER TABLE user_settings CHANGE orderWebhookUrl order_webhook_url ...` (data-preserving rename), applied directly to staging. Root migration file fixed in `package-database` PR #6.

## How to avoid this going forward

Any raw-SQL migration that adds a column must derive the DB column name the same way the naming strategy would (snake_case of the entity property), **not** copy the TypeScript property name verbatim. When in doubt, generate the migration with `typeorm-cli migration:generate` against the actual entity instead of hand-writing the SQL — the CLI applies the naming strategy automatically and this class of bug can't happen.
