
## Encendido de prod Vio Commerce bajo demanda — Miguel
- Quién: Miguel (pedido de Angelo)
- Dónde: sub Azure 3d276f7e, AKS `vio-commerce-prod` (rg-vio-commerce-prod) + MySQL `vio-ecom-db-prod` (rg-vio-databases)
- Cuándo: 2026-09-22 09:10–09:13
- Contexto (corregido): el AKS y la MySQL los encendió Miguel el 21/09 con el script (el az CLI usa la cuenta de Angelo, por eso el activity log dice angelo@tipio.no). El tag `vio-power=on` de la MySQL no se llegó a poner, y el guard apagó la MySQL hoy a las 07:08. El AKS siguió Running, pero sin base.
- Hecho: `scripts/prod-power.sh commerce start`. MySQL a Ready, AKS Running, tags `vio-power=on` en los dos (el tag de la MySQL falló mientras estaba parada y se volvió a poner a mano). `api-ecom.vio.live` responde 200 y graph-ql responde (UNAUTHENTICATED sin token, OK). Los pods de base-api se reiniciaron solos al volver la DB.
- Notas: `api-commerce.vio.live` todavía apunta a la IP de Istio, pero no tiene host configurado y la conexión se resetea (dominio legacy). `dashboard` y `shopify-sync` no tienen DNS (ya se sabía).
- Pendiente: el cron `prod-power-guard` dio timeout hoy (06:53, 07:05 y 07:46). Como el tag decía `off`, podría haber apagado el AKS; ahora el tag está en `on` y no va a actuar. Falta subirle el timeout. Vio Backend prod sigue apagado.
- Causa raíz: `prod-power.sh start` ponía el tag de la MySQL **antes** de encenderla. Con la base Stopped, `az tag update` falla (`ServerNotExist`). El 21/09 ese error se anotó como inofensivo sin verificar el tag, y quedó en `off`.
- Arreglo: el script ahora pone el tag de la base **después** del start, reintenta, verifica el valor y muestra el tag de la MySQL en `status`. Lo mismo para la PG de backend. Lesson: `docs/lessons/tag-en-flexible-server-stopped.md`.
