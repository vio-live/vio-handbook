# Session — 2026-09-03 — RN SDK: capa live, carrito al core, componentes, pagos nativos, beta y doc

> El SDK de React Native pasó de "headless y sin publicar" a **beta publicada en npm, con
> componentes, pagos nativos y documentación pública**. `react-native-sdk` @ **`5b60121`**
> (main), `vio-docs` @ **`b4151b2`** (main), `@vio-live/react-native-sdk@0.1.0-beta.1`.

## TL;DR

- **Publicado**: `@vio-live/react-native-sdk@0.1.0-beta.1`, tag `beta`. ⚠️ npm pone
  `latest` en el primer publish pase el tag que pases — hoy ambos apuntan a la beta.
  La doc **no** la enlaza.
- **Doc pública**: 13 archivos en `vio-docs/content/react-native/`, estructurada sobre

- **Verificado contra staging**: bootstrap → catálogo → carrito → checkout, con key real.

## Los cuatro bugs

Ninguno lo detectaban los tests unitarios; los cuatro eran silenciosos.

1. **REST autenticaba con el header equivocado.** `validateApiKey` lee
   `req.query.apiKey || req.headers['x-api-key']` y nada más. El SDK mandaba
   `Authorization` → **401 en todo `/v2/mobile/*`**. El `Authorization` pelado sí es
   correcto en el GraphQL de commerce; son dos capas distintas.
2. **El tipo del bootstrap no coincidía con el cable.** Declaraba `campaignId` plano y
   un bloque `market`; `GET /v2/mobile/config` no devuelve ninguno de los dos — devuelve
   `{ endpoints, campaign, primarySponsor, secondarySponsors, features }`. Resultado:
   placements en `[]` y el socket nunca conectaba. El tipo venía del web SDK, que lo
   heredó de un modelo viejo de iOS. **El tipo del web SDK sigue mal.**
3. **Cada `useCart()` tenía su propio `useState`.** Dos eran dos copias del mismo
   carrito del servidor, y con `autoCreate` dos montándose juntas creaban **dos carritos**
   en el backend.
4. **Cada entry publicada es un bundle CJS independiente** (CJS no tiene code splitting),
   así que `./react` y `./ui` tenían cada uno su `createContext` — y su propio `Vio`.
   Los componentes **nunca** podían ver al provider. Solo aparece instalando el paquete;
   se arregló anclando contexto y fachada en `globalThis`, como hace el web SDK.

## Hallazgos de backend (no son del SDK)

- **El caché de productos devuelve filas rotas.** Con `useCache: true` —el default del
  SDK— `Products` falla entero: `Cannot return null for non-nullable field Product.tags`.
  Con `useCache: false` los 6 productos del canal Bohus vuelven limpios. Reproducible.
  **Hoy `getProducts()` no funciona contra ese canal con el default.**
- **Staging tiene su propio GraphQL** (`graph-ql-staging.vio.live`). La tabla del web SDK
  dice que comparte el de dev. Corregido en RN; **el web SDK sigue con el valor viejo**.
- **`getStripeIntent` / `getKlarnaOrder` / `getVippsPayment` del SDK apuntaban a la nada**:
  a `apiBase` (capa Vio) cuando los handlers viven en `vio-shopcart-microservice` detrás
  de base-api, en paths que piden un `channelUserId` que el SDK no tiene. Nadie los
  llamaba. Documentados en el lugar; la reconciliación va por `getCheckout()`.
- **Klarna nativo ya estaba en el gateway** (`CreatePaymentKlarnaNative` /
  `ConfirmPaymentKlarnaNative`, con `client_token`). El SDK de RN nunca las llamó.
- **El mismo método de pago se escribe de dos formas**: `/v2/mobile/config` dice
  `apple_pay`, `CreateCheckout` responde `Apple Pay`.

## Decisiones tomadas

- **Un carrito, un sponsor.** Vio Commerce ata el carrito a un channel y cada sponsor es
  su channel, así que multi-sponsor = dos carritos, dos checkouts, dos pagos. Fuera de
  alcance por decisión de Angelo (el web SDK sí tiene `Map<sponsorId, cart>` si vuelve).
- **`VioCheckout` es pantalla, no overlay** — cierra la decisión abierta #3 del plan. El
  host conserva su navegación; si lo quiere en modal, lo envuelve.
- **Los SDKs de pago son dependencias reales**, no solo un seam de adapters. Angelo lo
  pidió explícito: "la idea es que todo sea lo más nativo posible". Van como **peers
  opcionales en entries separadas** (`/payments/stripe`, `/payments/klarna`) porque Metro
  bundlea todo `require` que ve — importar la entry *es* optar por la dependencia.
- **Expo funciona**, y Expo Go alcanza hasta que entran los pagos nativos. Cierra la
  decisión abierta #2 del plan.
- **La identidad sigue al web SDK**: `anonId` (device, persistido, no es un usuario de
  Vio), `customerSessionId` (carrito), `externalUserId` (la persona, **id del partner**,
  solo vía `identify()` post-login). Nunca email ni nombre.

## La asimetría iOS/Android (lo que se documentó)

CocoaPods resuelve las dependencias nativas del podspec de cada paquete → `pod install`
suele alcanzar. **Gradle solo mira los repos que declara la app**, y Klarna publica sus
artefactos de Android en su propio CDN:

```groovy
allprojects { repositories { maven { url 'https://x.klarnacdn.net/mobile-sdk/' } } }
```

Sin eso **falla solo Android** y iOS compila perfecto, así que se lee como bug de la app.
Stripe además pide `compileSdk` 36 y **Kotlin 2.x**, que es app-wide y puede chocar con
otras librerías. Y las fuentes se resuelven por **PostScript name en iOS** y **nombre de
archivo en Android** — mismo valor de theme, dos búsquedas distintas.
