### Causa raiz
La cuota `Standard EASv5 Family vCPUs` en NorwayEast esta en **limit 0** (uso 0/0). El nodepool necesita 4 cores. El VMSS `aks-e2aspool-29962209-vmss` quedo con capacity 0 y cada intento de `virtualMachineScaleSets/write` falla con:

Coincide con el fin de creditos de la suscripcion Sponsorship el 16/09: la cuota de esa familia se puso a 0.

### Causa secundaria (ya corregida)
El cron `qa-cluster-start` (08:00 L-V) reporto "ok" sin ejecutar nada. Corrio con el modelo de fallback `azure-openai/gpt-4o`, que no expuso la tool `exec` y devolvio "La herramienta az.aks.show no esta disponible". `toolsAllow` ya era correcto (`exec,read,write`); el problema era el modelo.
Fix aplicado: `openclaw cron edit <id> --model anthropic/claude-sonnet-5 --fallbacks google/gemini-3-6-flash --tools exec,read,write` en `qa-cluster-start` y `qa-cluster-stop`. Verificado.

- Standard DASv5 Family vCPUs: 0/22 (familia de prod `vio-commerce-prod`, D4as_v5 — sigue disponible)

- Resto de familias: limite por defecto 10

`az quota update` a 10 cores fallo con `QuotaNotAvailableForResource`: en Sponsorship sin creditos no hay self-service, requiere ticket/reactivacion de billing.

### Hecho
- `az aks start` ejecutado manualmente: no sirve, falla por cuota.
- Provider `Microsoft.Quota` registrado en la suscripcion (era necesario para consultar/pedir cuota).
- Crons de encendido/apagado de QA pinneados a modelo fiable.

### Pendiente (decision de Angelo)

## Staging RESUELTO — nodepool migrado a E2as_v4 y escalado a 3 nodos — Miguel

- Quien: Miguel. Angelo: "lo que me importa es que staging se levante".
- Cuando: 2026-09-18, 10:50-11:25 CEST.
- Resultado: **staging arriba**, 56 pods Running, endpoints verificados.

### Pasos ejecutados
1. `az aks nodepool add` fallo con `OperationNotAllowed`: habia un start trabado (operation ID `92293127-e374-4892-a7e4-dd7333d8b29a`, iniciado 07:54:32 UTC) reintentando el scale-up del VMSS contra cuota 0.
2. `az aks operation-abort -g qa -n kubernetesqa` -> `provisioningState=Canceled`. Esto destraba el cluster.
3. `az aks nodepool add -n e2asv4pool --node-vm-size Standard_E2as_v4 --node-count 2 --mode System --node-osdisk-size 128 --max-pods 250 --kubernetes-version 1.35.7` -> Succeeded, 2 nodos Ready en ~1 min.
4. 4 pods quedaron en `PodInitializing`. Causa: **saturacion de CPU**, no de RAM (ver abajo). Escalado a 3 nodos (`az aks nodepool scale --node-count 3`) y borrados los 4 pods para que reprogramaran.
5. `az aks nodepool delete -n e2aspool` (el viejo E2as_v5, 0 nodos).
6. Reconcile del `provisioningState=Canceled` con `az aks update`.

### Hallazgo importante: staging esta limitado por CPU, no por memoria
Con 2 nodos, el nodo 0 llegaba a **99% de CPU requests (1896m/1900m) con solo 27% de memoria**. Con 3 nodos: 86% / 36% / 17% de CPU.

Esto invalida el criterio con el que se eligio E-series (memory-optimized) para QA: el cluster no necesita RAM, necesita vCPU. Los 16 GiB por nodo estan ociosos al ~25%. Un D4as_v5 (4 vCPU / 16 GiB, cuota DASv5 = 22 disponible) daria el doble de CPU con la misma RAM y menos nodos. Queda como propuesta de right-sizing, no ejecutado.

### Estado final verificado
- Nodepool: `e2asv4pool`, Standard_E2as_v4, 3 nodos, System, k8s 1.35.7, provisioningState Succeeded.
- Cluster: powerState Running, provisioningState Succeeded, upgradeChannel `patch` (se restauro: el `az aks update` de reconcile lo habia puesto en `none`).
- Pods: 56 Running, 2 Completed, 0 pendientes.
- `https://api-ecom-staging.vio.live/` -> 200
- `https://api-ecom-dev.vio.live/` -> 200
- `https://graph-ql-staging.vio.live/graphql` -> responde desde la app (`UNAUTHENTICATED` por falta de API key, o sea stack completo funcionando)
- `https://graph-ql-dev.vio.live/graphql` -> idem

### Costo
3 x E2as_v4 a 0.180 USD/h = 0.54 USD/h. Con el horario actual (~365 h/mes) ~197 USD/mes, contra ~118 USD/mes de los 2 x E2as_v5 previos. El aumento es por el tercer nodo, que hacia falta por CPU — no por el cambio de SKU.
