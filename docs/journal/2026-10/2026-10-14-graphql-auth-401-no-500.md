# graphql: una key que no es de channel daba HTTP 500

## Goal

En QA, el web-sdk mandó una key que no es de channel (la de plataforma o una surface key).
`POST https://graph-ql-staging.vio.live/` con `Payment.GetAvailablePaymentMethods` respondió
**HTTP 500**. Tenía que ser **401 / `UNAUTHENTICATED`**. Angelo aprobó el arreglo el 14/10.
Condiciones: no cambiar quién pasa y quién no, y no tocar la excepción por nombre de operación
(`GetPurchaseConditions` / `IntrospectionQuery`), que tiene su propia tarea.

## Causa (reproducida con el ApolloServer real y un middleware falso)

Apollo Server 3.13 con una operación que falla y sin `data` responde con
`response.http.status || 400`. El que lo pisa es `StatusErrorResponsePlugin` en
`willSendResponse`: mapea `errors[0].extensions.code` y manda 500 si no conoce el code.

| Caso | Quién tira | code | Antes | Después |
|---|---|---|---|---|
| middleware 401 (key inválida, sin channel_user, sin header) | `AuthPlugin.ts:39` `ApolloError(..., 'UNAUTHENTICATED')` | `UNAUTHENTICATED` | 500 | **401** |
| middleware 200 sin `userChannelId` | `Utils/Auth.ts:57` `UnauthorizedError` | `INTERNAL_SERVER_ERROR` | 500 | **401** `UNAUTHENTICATED` |
| channel sin asignar | `Utils/Auth.ts:81` `ApolloError(..., 'UNAUTHENTICATED')` | `UNAUTHENTICATED` | 500 | **401** |
| middleware 5xx, caído o timeout | `AuthPlugin` | `UNAUTHENTICATED` | 500 | 500 `INTERNAL_SERVER_ERROR` |

1. **El plugin solo conoce nombres de clase.** `StatusErrorResponsePlugin.ts:14-18` traduce
   `InvalidArgumentError`, `NotFoundError` y `UnauthorizedError`. El code estándar de Apollo,
   `UNAUTHENTICATED`, no estaba y caía al default de 500 (`:34`).
2. **`formatError` nunca envuelve las excepciones de dominio.** `Exceptions/index.ts` exporta
   `CustomError as Exception`. En cambio, `UnauthorizedError`, `NotFoundError`,
   `InvalidArgumentError` y `ServerError` heredan de otra clase, `Exceptions/Exception.ts`. Por eso
   `err.originalError instanceof Exception` (`GraphQLServer.ts`, formatError) es siempre `false`.
   Todas salen con `code: INTERNAL_SERVER_ERROR` y HTTP 500. El mapeo por nombre de clase del
   plugin es código muerto.

## Decisions

- **No arreglar la herencia de `Exception`.** Si se arreglara, `NotFoundError` pasaría a 404 e
  `InvalidArgumentError` a 400 en todo el gateway. Por ejemplo, "Checkout not found" cuando shopcart
  está caído dejaría de ser 500. Queda fuera de alcance. El test fija que GetCheckout con
  shopcart 500 sigue respondiendo 500.
- **Que middleware esté caído no es un 401.** Si respondiera 401, el cliente podría descartar una
  key buena durante una caída. Sigue siendo 500 y cambia el code (`INTERNAL_SERVER_ERROR`).

## Blockers / open questions

- Los errores de dominio salen todos como 500 (causa 2). ¿Lo arreglamos? Habría que revisar qué
  esperan los clientes (web-sdk, apps) antes de que aparezcan los 404/400.
- La excepción por nombre de operación sigue igual. Tiene su propia tarea.
- `StatusErrorResponsePlugin` mira solo `errors[0]`. Si una respuesta tiene datos parciales y el
  primer error es de auth, ahora sale 401 con `data`. Ya pasaba lo mismo con los otros codes.
