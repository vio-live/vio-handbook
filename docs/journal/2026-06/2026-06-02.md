## 3. Migración de data Neon → Azure PostgreSQL (todos los entornos)

### Backup previo al rename
- Job `db-restore-job` en producción vieja tomó `pg_dump` desde Neon
- Guardado en: `saapivio/db-snapshots/prod-pre-rename-2026-06-01-1610.sql` (~323 MB)
- **Imagen requerida**: `postgres:17-alpine` (Neon corre PG17)

### Restore en producción
- Job `db-restore-job` en `rg-api-vio-production`
- Descarga SAS → `psql` Azure PostgreSQL dentro de VNet
- Status: **Succeeded** ✅
- Verificado: tablas con data (`shoppable_ad_activations: 107`, `polls: 39`, `broadcasts: 18`, ...)

### Restore en staging y development
- Jobs `db-restore-staging` / `db-restore-dev` creados vía ARM API
- SAS generado con `az storage blob generate-sas --account-key` (el user-delegation SAS daba 403)
- Status: **Succeeded** ✅ en ambos

### Problemas encontrados y solución
| Problema | Causa | Solución |
|---|---|---|
| SAS 403 | User delegation SAS expiró / permisos insuficientes | Generar con `--account-key` en lugar de `--auth-mode login` |
| `wget: bad address ''` | `$DOWNLOAD_URL` expandido vacío en heredoc shell | Construir JSON con `jq --arg` para que vars de runtime queden literales |
| SAS expirado en staging/dev | Token de 2h expiró antes de ejecutar | Generar con 4h de expiración |

## 4. Eliminación completa de Neon

### ⚠️ NEON YA NO EXISTE EN ESTE STACK

- **No hay proyecto Neon activo** para socket-server
- **No hay `NEON_URL`** en ningún Container App
- **No hay `@neondatabase/serverless`** en el código

### Cambios en `tipiodevelopment/socket-server`
- `server/db.ts`: eliminada toda la lógica dual-driver (Neon WebSocket vs pg). Ahora usa únicamente `pg` + `drizzle-orm/node-postgres`
- `scripts/seed-dev.ts`: reemplazado `neon()` + `drizzle-orm/neon-http` por `pg.Pool` + `drizzle-orm/node-postgres`
- `scripts/delete-non-demo-campaigns.ts`, `delete-test-client-apps.ts`, `backfill-multi-sponsor-phase2.ts`: `Pool` de `@neondatabase/serverless` → `Pool` de `pg`
- `package.json`: `@neondatabase/serverless` eliminado

### Estado actual de DATABASE_URL por entorno
Todos apuntan a Azure PostgreSQL privado dentro de VNet:
- production: `postgresql://pgadmin:...@pg-api-vio-production.postgres.database.azure.com/socket_server?sslmode=require`
- staging: `postgresql://pgadmin:...@pg-api-vio-staging.postgres.database.azure.com/socket_server?sslmode=require`
- development: `postgresql://pgadmin:...@pg-api-vio-development.postgres.database.azure.com/socket_server?sslmode=require`

### Para desarrollo local
```bash
docker compose up -d   # PostgreSQL 16 en localhost:5432
yarn dev               # DATABASE_URL=postgresql://pgadmin:localpass@localhost:5432/socket_server
```
