# Session — 2026-06-10 — Dashboard auth: Firebase IdP + roles/capacidades + multi-tenancy

> Arrancó como "levanta el backend en local" y terminó construyendo la
> autenticación + autorización real del dashboard de Vio (socket-server), que
> hasta hoy tenía una sesión **simulada** sin roles. Todo el trabajo de código
> está en **socket-server PR #41**; el detalle vive en
> `socket-server/docs/AUTH_AND_PERMISSIONS.md`. Decisiones formalizadas en
> [ADR-0007](../../decisions/0007-firebase-auth-single-idp.md) (authn) y
> [ADR-0008](../../decisions/0008-operator-authorization-capabilities-tenancy.md) (authz).

## Qué se construyó (arco de la sesión)

1. **Levantar backend local.** El repo no era un git repo (basura suelta). Re-clonado
   `tipiodevelopment/socket-server`. **`develop` es la canónica** (Angelo: "main lo
   tenemos aún desfazado"), pero develop aún importaba `@neondatabase/serverless` en
   `server/db.ts` y **Neon se eliminó el 2026-06-02** → parche local al driver `pg`.
   Server en **:5050** (el 5001 lo ocupa el emulador firebase de `~/claning-app`).

2. **Identidad compartida con Commerce (ADR-0007).** El dashboard usa el **mismo
   proyecto Firebase que Commerce** como IdP único. El backend **verifica** el ID
   token offline (JWKS de Google, sin service account, sin llamar a Commerce). Config
   pública extraída del bundle de `webapp-dev.vio.live` → proyecto **`reachu-qa`**
   (staging). **Un proyecto Firebase por entorno**; prod es otro (pendiente).

3. **F2/F3 — usuarios, roles, allowlist, gate.** Migración `0007` (`firebase_uid`,
   enum `role`, `sponsor_id`) + `0008` (`parent_admin_id`). Sesión = **cookie
   httpOnly** (los `fetch` ya mandan credentials → 0 call-sites tocados). **Allowlist
   estricta** (solo emails pre-aprovisionados; `ADMIN_EMAILS` bootstrapea el primer
   super_admin). Gate `app.use('/api')` que re-lee el rol por request.

4. **Modelo de autorización (ADR-0008).** Dos ejes: **capacidades** (matriz
   `rol→capacidades`, extensible) + **tenancy** (`admin` = tenant root dueño de sus
   apps/sponsors; `operator`/`viewer` pertenecen a un admin vía `parent_admin_id`;
   `super_admin` global). Listados scopeados por **sesión** (se eliminó el `?userId=`
   que mandaba el cliente — cerraba un hueco).

5. **UI de gestión de operadores** (`/users`, solo super_admin) + página `/login`
   (email/password + Google). Verificado end-to-end en navegador headless.

6. **División de apps reales entre usuarios.** El local solo tenía Allermedia. Las
   apps reales (Viaplay/TV2/VG) estaban en el snapshot de **prod**, todas bajo un
   solo usuario (`vio-admin`). Restauré prod en local (+ re-migré 0007/0008) y dividí:
   **Viaplay→`viaplay@vio.live`, TV2→`tv2@vio.live`, las dos VG→`vg@vio.live`**
   (admins; cuentas Firebase reales en reachu-qa, pw de test). Pregnancy fuera.
   Verificado: cada admin ve solo su app, super_admin las 13.

7. **Auditoría de apiKeys.** El gate `/api` tapaba 2 endpoints que se autentican por
   **apiKey** (no por sesión): `POST /api/checkout/confirm-apple-pay` (Apple Pay del
   SDK iOS) y `POST /api/campaign/payments/apikey/:apiKey`. **Arreglado** (exentos en
   `PUBLIC_API`). Confirmado que `/v2/*` y `/v1/*` (SDK) nunca estuvieron gateados.

8. **Documentación.** `socket-server/docs/AUTH_AND_PERMISSIONS.md` (referencia de
   código) + este journal + ADR-0007/0008.

## Decisiones (resumen — detalle en ADR-0007/0008)

- Firebase de Commerce = IdP único; backends separados, verificación offline.
- Allowlist estricta; `ADMIN_EMAILS` bootstrap.
- Roles: super_admin (global), **admin = tenant root (no global)**, operator (v1: solo crea campañas), viewer (lee su sponsor).
- Autorización = capacidades × tenancy (no jerarquía lineal).
- Scope por sesión, no por `?userId=` del cliente.
- Firebase **por entorno**; nunca apuntar prod a `reachu-qa`.
