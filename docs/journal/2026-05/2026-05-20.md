# 2026-05-20 — Investigación de lentitud en QA

## Contexto

Angelo reportó que QA iba lento, especialmente el `add to cart`. Se investigó la causa raíz comenzando por nodos AKS, Redis, Firestore y terminando en MySQL.

## Hallazgos

### Lo que NO era el problema

| Hipótesis | Resultado |
|-----------|-----------|
| Nodos AKS saturados | 3 nodos activos, 7-8% CPU, sin MemoryPressure |
| Redis | Sano. 3.94MB usados, PONG <1ms, sin conexiones rechazadas |
| Firestore | Enruta a Stockholm (4ms TCP). Solo se usa para tracking events (4ms) |
| Locks MySQL | Solo 11 row lock waits totales, máx 508ms |
| Latencia de red a MySQL | MySQL en Hetzner Helsinki — **0-1ms TCP desde Norway East** |

### La causa raíz: N+1 queries en TypeORM

El `add to cart` hace **25+ queries secuenciales** contra MySQL. TypeORM carga cada relación del producto por separado en lugar de usar JOINs. Con ~30ms de overhead de TypeORM por query (mapeo de entidades), el total suma ~1.7s.

Traza real capturada con MySQL general log durante un add-to-cart:

```
+179ms  SELECT DISTINCT Product_id     ← paginación TypeORM
+92ms   SELECT Product
+192ms  SELECT ProductShipping
+142ms  SELECT DISTINCT Variant_id     ← paginación TypeORM
+36ms   SELECT Variant
+38ms   SELECT cart_item existente
+60ms   SELECT DISTINCT Product_id     ← segunda vez (!)
+54ms   SELECT Product                 ← segunda vez (!)
+35ms   START TRANSACTION
+35ms   INSERT INTO price_data
+35ms   COMMIT
+35ms   START TRANSACTION
+35ms   INSERT INTO cart_item
+35ms   COMMIT
+35ms   START TRANSACTION
+35ms   UPDATE cart total
+35ms   COMMIT
+53ms   SELECT checkout (respuesta final)
```

**Total DB: ~1.3s** solo en el happy path con 1 producto en el carrito. Escala con cada item adicional.

El mismo patrón afecta `GET /cart`, `GET /products` y `GET /available-payment-methods`.

### Problema adicional: connection pool de 1

TypeORM estaba usando **1 sola conexión** al MySQL (sin pool configurado). Con usuarios concurrentes:
- Usuario 1 hace add-to-cart (1.7s de DB)
- Usuario 2 espera 1.7s para obtener la conexión
- Usuario 3 espera 3.4s

## Cambios aplicados

### MySQL — índices creados

```sql
-- product: evita full table scan en COUNT queries (3836 llamadas/sesión)
CREATE INDEX idx_product_status_deleted ON product (status, deleted_at);
CREATE INDEX idx_product_deleted ON product (deleted_at);

-- imported_product: evita full table scan en queries de conteo
CREATE INDEX idx_imp_deleted ON imported_product (deleted_at);
CREATE INDEX idx_imp_shopify ON imported_product (shopify_id);
CREATE INDEX idx_imp_woo ON imported_product (woo_id);
```

Mejora por query: ~20-40%. No resuelve el N+1, pero reduce el load global de DB.

### MySQL — flush log

```sql
-- QA únicamente. Reduce overhead de COMMIT (flush cada segundo en vez de cada COMMIT)
SET GLOBAL innodb_flush_log_at_trx_commit = 2;
```

⚠️ No aplicar en producción sin evaluar trade-offs de durabilidad.

### Shopcart — connection pool

```bash
# Permite hasta 10 conexiones concurrentes al MySQL
kubectl set env deployment/shopcart TYPEORM_EXTRA='{"connectionLimit":10}' -n default
```

## Fix pendiente (requiere backend)

El problema de fondo requiere cambios en el código del `shopcart`:

### Opción A — QueryBuilder con JOINs (recomendada)

Reemplazar las cargas con eager relations por un QueryBuilder explícito:

```typescript
// En lugar de:
const product = await productRepo.findOne({
  where: { id },
  relations: ['variants', 'images', 'productShippings', 'productShippings.shipping']
});

// Usar:
const product = await productRepo
  .createQueryBuilder('product')
  .leftJoinAndSelect('product.variants', 'variant', 'variant.deleted_at IS NULL')
  .leftJoinAndSelect('product.images', 'image')
  .leftJoinAndSelect('product.productShippings', 'ps')
  .leftJoinAndSelect('ps.shipping', 'shipping')
  .where('product.id = :id', { id })
  .getOne();
```

Pasa de ~8 queries a 1. Impacto estimado: reducir add-to-cart de 1.7s a ~300-400ms.

### Opción B — Cache Redis por producto

Cachear el objeto producto completo en Redis con TTL de 5 minutos:

```typescript
const cacheKey = `product:${productId}`;
const cached = await redis.get(cacheKey);
if (cached) return JSON.parse(cached);

const product = await loadProduct(productId);
await redis.setex(cacheKey, 300, JSON.stringify(product));
return product;
```

Útil como complemento de la Opción A para productos muy consultados.

### Endpoints afectados por el mismo patrón

| Endpoint | Tiempo actual | Causa |
|----------|--------------|-------|
| `POST /cart/:id/item/add` | ~1.7s | N+1 carga producto + relaciones |
| `GET /cart/:id` | ~270ms | N+1 carga items del carrito |
| `GET /channel/available-payment-methods/:id` | ~80ms | Múltiples queries de conteo |
| `GET /products` | Sin medir (mismo patrón) | N+1 por cada producto en lista |
| `POST /checkout/apple-pay/confirm` | ~7.7s | API externa de Apple Pay (no optimizable desde infra) |

## Recomendación para producción

Antes de migrar a otra cloud, es crítico resolver el N+1 en el shopcart y products service. La lentitud no es de infra — sobrevivirá a cualquier migración si no se corrige en código.
