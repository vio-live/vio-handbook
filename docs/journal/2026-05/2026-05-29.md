# Sesión — 2026-05-29 — Socket Server: Nueva Infraestructura + CI/CD

## Objetivo

Crear infraestructura completa para `tipiodevelopment/socket-server` (el backend de Vio Commerce) con 3 entornos independientes (production, staging, development), sin AKS ni Kubernetes, usando Azure Container Apps + PostgreSQL Flexible Server, gestionado con Terraform.

---

## Problemas resueltos en vio-infra-tf

### 1. Pipeline roto: `outbound_ip_ids` no válido en azurerm v4

**Causa**: azurerm v4 renombró el argumento `outbound_ip_ids` → `outbound_ip_address_ids` en `load_balancer_profile`.

**Fix** (`vio-infra-tf/aks.tf`):
```hcl
load_balancer_profile {
  outbound_ip_address_ids = [data.azurerm_public_ip.outbound_prod.id]
}
```

### 2. AKS network_plugin drift (cluster destruction risk)

**Causa**: Terraform tenía `network_plugin = "kubenet"` pero los clusters reales usan `azure/overlay`. Sin corregir, `terraform apply` destruiría ambos clusters.

**Fix** (`vio-infra-tf/aks.tf`): Actualizado a `network_plugin = "azure"` + `network_plugin_mode = "overlay"` para que coincida con la realidad.

### 3. SP `vio-infra-tf-cicd` deshabilitado

El SP estaba deshabilitado como medida de mitigación post-incidente 2026-05-23. Reactivado con:
```bash
az ad sp update --id b9bb7f7c-cd80-446d-9251-2572d9bcb546 --set accountEnabled=true
```

## Nueva infraestructura: socket-server

### Arquitectura

- **Azure Container Apps** (WebSocket nativo, `transport = "auto"`, escala a 0 en staging/dev)
- **Azure PostgreSQL Flexible Server** (acceso privado por VNet, sin public access)
- **Managed Certificate** (TLS automático por Azure)
- **User Assigned Identity** para pull desde ACR sin credenciales
- Todos los entornos comparten el mismo ACR (`reachuprod2.azurecr.io`)

### Repositorio Terraform: `vio-live/vio-infra-tf`

Archivos nuevos/modificados:
```
vio-infra-tf/
├── environments.tf                          # NUEVO — fuente única de verdad para los 3 entornos
├── variables.tf                             # Añadida variable `location` (default: norwayeast)
├── main.tf                                  # Añadido provider `random ~> 3.0`
├── aks.tf                                   # Fix outbound_ip_address_ids + network_plugin azure/overlay
└── modules/socket-server-env/
    ├── main.tf                              # NUEVO — módulo completo
    ├── variables.tf                         # NUEVO
    └── outputs.tf                           # NUEVO
```

## CI/CD: `tipiodevelopment/socket-server`

### GitHub Actions workflow (`.github/workflows/deploy.yml`)

- **Push a `main`** → deploy automático a `development`
- **`workflow_dispatch`** → deploy a cualquier entorno (production / staging / development)
- Autenticación: **Azure OIDC** (sin credenciales estáticas)
- Steps: checkout → build Docker → push a ACR → `az containerapp update`

### GitHub Secrets requeridos (`tipiodevelopment/socket-server`)

| Secret | Valor |
|---|---|
| `AZURE_CLIENT_ID` | OIDC federated credential |
| `AZURE_TENANT_ID` | `0c592ce5-257d-49de-b50b-4ac1fbc6fb05` |
| `AZURE_SUBSCRIPTION_ID` | `3d276f7e-0783-4581-8a49-ad0a2c432c63` |

### Dockerfile (reescrito)

Multi-stage build limpio. Migraciones de Drizzle se ejecutan en startup del contenedor (`drizzle-kit push && node dist/preserver.js`) porque la BD es privada (VNet) y CI no puede acceder directamente.
