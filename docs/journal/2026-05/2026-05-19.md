### Vipps Express investigation (deferred to future sprint)

User asked: "could the user just enter a phone number and have Vipps return their address?" — that's Vipps Checkout / Express. Investigation:

1. Commerce only exposes `CreatePaymentVipps(checkout_id, email, return_url) → payment_url` (the basic eCom redirect). No confirm, no address-return, no Express endpoint.
2. The Vipps Checkout API itself (`POST /checkout/v3/session`) requires per-merchant credentials commerce holds; only supports **static** shipping options (no dynamic-from-address); and per Vipps's own docs is **transitioning to Kustom** — building on it now is building on a sunset product.

Documented in [`socket-server/docs/ROLLOUT_ROADMAP.md` Phase 3.6](#) (commit `2d333ca` on socket-server `develop`) with three resumption paths (real prototype / mock prototype / spec-only). Recommended **C (spec for Commerce team)** when picked up.

## Decisions

- **Don't pursue Vipps Express now**: Commerce backend doesn't expose it, and Vipps Checkout is being deprecated → Kustom. Wait until Commerce evaluates Kustom and offers an endpoint, then revisit. Documented in `ROLLOUT_ROADMAP.md` 3.6, not in an ADR (no architectural commitment, just a defer).
- **Stripe Link is not exposed as a separate method in the SDK**: `availableMethods` collapses `stripelink → stripe` so the user always sees one "Card" button → native PaymentSheet.
- **Multi-sponsor cart cards stay as cards**: when the user asked "make multi-sponsor look like legacy", the *content* of the rows was what was unified (via `VCartItemRow`), not the structure. The card-per-sponsor IS the multi-sponsor — removing it would defeat the purpose.
