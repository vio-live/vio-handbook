# Sesión — 2026-05-26/27 — Incident Recovery + Hardening

## Contexto / Root Cause

El 2026-05-23, el workflow de GitHub `vio-live/vio-infra-tf` (ID `279799839`) ejecutó `terraform apply` automáticamente en push a `main`. La autenticación usaba el SP `vio-infra-tf-cicd`. El estado de Terraform estaba vacío (posiblemente no tenía acceso al backend de Azure Blob), lo que resultó en que Terraform consideró todos los recursos como "por crear" — y primero los **destruyó**.

**Resultado**: ambos clusters AKS (`reachu-prod` y `kubernetesqa`) eliminados. Outage total de prod y QA.

---

## Acciones de mitigación inmediata

1. Deshabilitado SP `vio-infra-tf-cicd` (`b9bb7f7c-cd80-446d-9251-2572d9bcb546`) vía `az ad sp update`
2. Deshabilitado workflow `279799839` vía GitHub API

## Hardening implementado

### Terraform CI/CD
- Workflow actualizado: **apply solo en `workflow_dispatch` con `apply: true`** — nunca automático en push

## Lecciones aprendidas

1. **Terraform apply automático en CI es peligroso** — siempre requerir aprobación manual
2. **tfstate vacío = destrucción total** — el remote state backend debe ser accesible antes de ejecutar apply
3. **IPs dinámicas requieren actualizar DNS** — usar IPs estáticas desde el inicio
4. **Los manifiestos K8s deben vivir en git** — no solo aplicados manualmente
5. **MySQL firewall bloqueará el nuevo cluster** — documentar IPs de egress como parte del onboarding
