# Session — 2026-08-18 — applyVioTheme, un choque real (y arreglado), sandbox package personal

## `applyVioTheme` — API pública de theming (colores/fuentes)

Motivación: Vev y (pronto) Replit necesitan poder exponer un panel de "marca"
(colores/fuentes) sin que cada plataforma reinvente cómo tocar el SDK.
Investigación primero: **todos los componentes ya usaban `var(--vio-color-*,
fallback)`/`var(--vio-font-*, fallback)`** — un sistema de tokens completo
(`VioTokens`, `tokens.ts`) ya existía, exportado desde `/ui` pero sin una
forma pública de sobreescribirlo.

Agregado (`vio-web-sdk` `b61a760`): `applyVioTheme({ colorAccent, fontSerif,
... })` — set de estilo inline en `:root` (gana sobre el stylesheet inyectado
sin pelear especificidad), subconjunto curado (solo colores + fuentes, no los
~30 tokens) a propósito. Verificado en vivo en el demo local: el texto de
`<vio-product-carousel>` (shadow DOM) cambió de color correctamente al
llamar la función — confirma que las CSS custom properties SÍ atraviesan el
shadow boundary como se esperaba.

**Bug encontrado al integrar**: `_vev-entry.ts` (por donde pasa el bundle de
Vev) reexporta `core` + `react`, pero `react/index.ts` nunca importaba
`tokens.ts` — solo `ui/elements.js` directo. Resultado: `applyVioTheme`
quedaba inalcanzable desde Vev aunque estuviera en `/ui`. Fix (`ed514eb`):
`react/index.ts` ahora importa y reexporta `tokens.js` también. Confirmado
con grep sobre el bundle regenerado (antes 0 ocurrencias, después 2).

Publicado: npm **`@vio-live/web-sdk@0.4.0`**.

ampliada: **chequear el timeline de versiones (deploys sin commit detrás)
inmediatamente antes de cada `vev deploy`, no solo al principio de la
sesión.**

## Package sandbox personal — arreglo estructural, no solo disciplina

Angelo: "¿no podemos tener mi propio vev.json?" — la raíz real del problema:
`vev deploy` no tiene staging ni lock, cualquiera que deploye pisa el
`current` sin preguntar, sin importar quién.

Solución (`vio-vev` `daa288a`): cuenta Vev **separada** de Angelo (confirmado
"siempre hemos tenido cuenta separada" — distinta del team Vio que es dueño
de `cq1lXld-TA9`), package nuevo creado ahí (`cF67JS--lMi`, vía `vev init`
en un directorio aislado — correr `vev init` donde ya existe `vev.json` no
crea nada, solo dice "Already initialized"). Patrón:

- `vev.json` (sin sufijo) = el ÚNICO compartido, siempre commiteado, siempre
  `cq1lXld-TA9`. Nunca cambiar a qué apunta.
- `vev.<nombre>.json` = sandbox personal, gitignorado (`vev.*.json` en
  `.gitignore` — verificado que el patrón NO atrapa `vev.json` sin sufijo).
- `npm run sandbox:on`/`sandbox:off` — copia el config personal sobre
  `vev.json` para iterar, y lo restaura con `git checkout -- vev.json`
  (siempre seguro, es lo commiteado).

**Pendiente sin resolver**: no confirmado si la cuenta separada de Angelo
tiene permiso de ESCRITURA sobre `cq1lXld-TA9` (el meta endpoint respondió
200, pero eso no prueba acceso de deploy) — no se testeó con un deploy real
para no arriesgar. Antes del próximo deploy real al package compartido,
confirmar esto primero (o volver a loguear con las credenciales del team
Vio si hace falta).
