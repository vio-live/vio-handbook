# Session — 2026-07-15 — Vev: bloques nativos, picker modal, variantes y audit

> Continuación del 2026-07-09. Aquel día envolvimos el `vio-web-sdk` en Vev; esta sesión el
> enfoque **maduró a su forma definitiva**: *compartir el CORE del SDK, poseer la UI en Vev*.
> Salieron 7 bloques, el picker modal, manejo real de variantes/combinaciones, y un audit de
> limpieza. Arquitectura completa en
> [`architecture/vio-vev-integration.md §6`](../../architecture/vio-vev-integration.md).

## Arco de la sesión

1. **Decisión de arquitectura (§6.7).** Angelo quería que "la integración con Vev vaya por libre"
   pero manteniendo funcionalidades linkeadas. La tensión se resolvió trazando la línea en la capa
   correcta: el **core es headless** (no dibuja) → compartirlo nunca condiciona el diseño; la **UI
   sí tiene opinión** → poseerla en Vev. Detonante: para que el card se viera como VG quería tuve
   que editar componentes UI **compartidos** del SDK, que heredaban todos los consumidores.

2. **Product Card nativo + Carousel + Grid.** El card dejó de usar `<vio-product>` y pasó a UI
   propia (`ProductCardView` compartido) llamando al core. Sobre esa base salieron el **Carousel**
   (scroll-snap, N visibles, flechas, heading editorial) y el **Grid** (columnas configurables).
   Config de card compartida en `card-props.ts` + `editableCSS` (9 selectores reestilizables).

3. **Addons de acción.** Tres bloques `type: "action"` que se **adjuntan a cualquier elemento**
   (imagen, shape, texto): Add to Cart, Open Product Info, Open Cart. El editor diseña, nosotros
   ponemos el comportamiento.

4. **Picker modal — y el crash.** Un modal con `createPortal(document.body)` desde el panel de
   propiedades **crashea el editor de Vev**. La pista la dio el picker legacy de Alan: usa
   **`SilkeModal`**. Reescrito sobre Silke → funciona. Segundo crash: props `type: "array"` con
   editor custom también revientan → la lista se guarda como `{ ids: "1,2,3" }` (string plano).

5. **Variantes y combinaciones (§6.8).** Resolución de variante por **match de token**
   (`"30"` ∈ `"30 ml"` pero `"M"` ∉ `"Medium"`), combinaciones sin stock deshabilitadas, y el
   carrito preciando por la **variante seleccionada**. Un intento intermedio de match "exacto
   estricto" rompió el caso real (`"30"` vs `"30 ml"`) — quedó documentado como aviso.

6. **Bug de precios → resultó ser DATA (§6.9).** El detalle mostraba `3 310,14 kr` donde la card
   decía `300 NOK`. Angelo intuyó que era el formato del precio, no el nombre ni la moneda como
   tal. Verificado contra el backend: las **variantes traen `currency_code: "EUR"` con un amount
   que ya es NOK** → al pedir NOK se convierte ×11. **Es para Alan**, brief en §6.9.

7. **Audit de limpieza.** `withRetry()` unificado (3 loops duplicados → 1), tipos compartidos,
   logs tras flag `DEBUG`, y **skeleton + placeholder de error** en los cards (antes: cuadro gris).

## Lecciones (ya en §6.2)

- `SilkeModal`, nunca `createPortal` crudo, desde el panel de propiedades.
- Props `array` + editor custom = crash. Usar `object` con campo string.
- El manifest renombra `editableCSS`→`editableCSScomputed` y `children`→`contentChildren`;
  las claves crudas salen `null` (no concluir que no se aplicaron).
- El `widgetId` sale del **nombre de la función**, no del `name` visible → renombrar el `name` es
  seguro, renombrar la función huérfana las instancias.
