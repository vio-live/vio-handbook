### Code review del token refresh — vio-shopify-sync (branch staging)

**Flujo actual:**
1. `@shopify/shopify-app-react-router` maneja OAuth y token refresh automático dentro de `authenticate.admin()`.
2. `resolveShopifyAuth()` en `app/lib/vio.server.ts` pasa accessToken + refreshToken al backend Vio via `POST /api/users/me/sales-channel`.
3. Auto-connect via Redis login token en `app/routes/app._index.tsx`.

**Race condition confirmada (riesgo ALTO):**
No hay ningún mecanismo de locking. Si múltiples pods llaman `authenticate.admin()` con un token expirado simultáneamente, cada uno intenta refresh independiente. Shopify invalida el refreshToken tras el primer uso → los demás pods fallan.

**Propuesta de distributed lock de Alan es correcta.** Patrón recomendado:
- `SET shopify:refresh-token:{connectionId} NX EX 30` antes del refresh
- Pod que obtiene lock: refresca, escribe nuevo token, libera lock
- Pods sin lock: esperan y re-leen el token actualizado de Redis

**Complicación:** El refresh vive dentro de la librería de Shopify (`authenticate.admin()`), no en código de app. Opciones: wrappear la llamada con lock a nivel aplicación, o implementar un session storage adapter custom con CAS.

**Otros issues detectados:**
1. No hay refresh proactivo — si ningún merchant visita la app por semanas, el token expira y el backend Vio falla al usar webhooks
2. Sin recovery path si el refresh token mismo expira
3. Dos clientes Redis independientes (session storage + login tokens) — duplica conexiones a Upstash
4. `webhooks.app.scopes_update.tsx` escribe a Prisma/SQLite aunque prod usa Redis para sessions — escritura muerta
